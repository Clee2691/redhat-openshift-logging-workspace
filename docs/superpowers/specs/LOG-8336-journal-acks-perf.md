# LOG-8336 — Performance cost of sink acknowledgements for journald collection

**Status:** Investigation complete (design input)
**Jira:** [LOG-8336](https://redhat.atlassian.net/browse/LOG-8336) (spike, **Closed/Done**) · relates to [LOG-7538](https://redhat.atlassian.net/browse/LOG-7538) (fix, **Assigned/In Progress**)
**Source:** [rhobs/redhat-openshift-logging-workspace#27](https://github.com/rhobs/redhat-openshift-logging-workspace/pull/27) — `docs/investigations/LOG-8336-journal-acks-perf/`
**Prior work:** [Clee2691/clo_investigations @ LOG-8336](https://github.com/Clee2691/clo_investigations/blob/LOG-8336/reports/LOG-8336-journal-loss-investigation.md)

## Problem

Collecting from journald on stock CLO 6.6 loses **5–10% of journal logs** when the collector
restarts under backpressure. (LOG-7538 originally demonstrated ~15% loss reading from journald; the
LOG-8336 prior work measured 5–10% on CLO 6.6.) The
cause: stock `AtLeastOnce` provisions a persistent disk buffer for the Loki sink but does **not**
emit a Vector sink `acknowledgements` block, so delivery is not acknowledged end-to-end. The
journald source advances its read checkpoint independently of confirmed sink delivery, so the
in-flight window (read but not yet durably delivered) is dropped on restart.

The LOG-8336 prior work established that enabling `acknowledgements.enabled = true` on the sink
prevents the loss. This spike answers the follow-up question that gates shipping that fix:

> **What is the throughput/latency cost of enabling sink acknowledgements?**

## Decision / Finding

**Enabling sink acknowledgements is performance-neutral.** The only property it changes is data
durability (a correctness property), so the LOG-7538 fix can be enabled without a measurable
performance regression.

- **Steady state (sink keeping up):** acks are essentially free — ~0% throughput change, Loki
  request RTT within noise (~1 ms), ~equal CPU, small memory increase (~12 MB).
- **Under backpressure:** no throughput or latency difference. With or without acks the collector
  fills the disk buffer at full source rate, then `when_full = block` stalls the journald source;
  delivered throughput is gated by Loki, not by the ack setting.
- **The difference is durability only:** acks close the in-flight window lost on restart
  (LOG-8336's 5–10% loss).

## Evidence

Environment: CLO 6.6.1 / Loki 6.6.1 / COO 1.5.2 on OpenShift; in-cluster Garage S3; LokiStack
`1x.demo` (single ingester); journald-only `infrastructure` input (`sources: [node]`) →
`lokiStack` output with `deliveryMode: AtLeastOnce` (256 MB disk buffer, `when_full = block`).
Load generated by a privileged `journal-injector` DaemonSet; metrics scraped from Vector internal
metrics via thanos-querier.

### Steady state, ~1300 ev/s

| Metric | Acks OFF | Acks ON | Δ |
|---|---|---|---|
| Sink delivered throughput | 1304 ev/s | 1309 ev/s | ~0% |
| Journal read rate | 1303.8 ev/s | 1302.9 ev/s | ~0% |
| Loki request RTT (avg) | 34.9 ms | 36.2 ms | +1.3 ms (~4%) |
| Buffer send duration (avg) | 1.60 ms | 2.12 ms | +0.5 ms |
| In-flight requests (avg) | 0.5 | 0.5 | 0 |
| Collector CPU | 0.431 cores | 0.423 cores | ~0% |
| Collector memory (working set) | 94 MB | 106 MB | +12 MB (~13%) |

### Backpressure (Loki ingester scaled to 0), disk-buffer fill from empty

| t (s) | Acks OFF — buffer events | Acks ON — buffer events |
|---|---|---|
| 0 | 0 | 0 |
| 18 | 42,289 | 70,319 |
| 36 | 67,996 | 70,319 |
| 54 | 69,520 (full) | 70,319 (full) |
| 72+ | 69,520 — source blocked | 70,319 — source blocked |

Both modes fill the disk buffer to capacity then block the journald source; delivered = 0
throughout. The journald source read rate tops out at ~1300 ev/s per node regardless of injector
worker count — the ceiling is systemd journald rate-limiting, not Vector or the injector.

## Methodology (reproducible)

The investigation directory (`docs/investigations/LOG-8336-journal-acks-perf/`) is self-contained:

- `manifests/` — journald-only `ClusterLogForwarder`, collector RBAC, privileged `journal-injector`
  DaemonSet + SCC RoleBinding.
- `scripts/bench-measure.sh` — steady-state snapshot (throughput, RTT, buffer, CPU/mem) via
  PromQL against thanos-querier for the collector pod on the target node.
- `scripts/bench-sample.sh` — time-series fill/drain sampling of source rate, delivered rate, and
  buffer growth.
- `scripts/build-cfg.py` — derives the acks-on config (and a fresh-buffer-id variant for clean
  backpressure fill curves) from the captured stock baseline.
- `configs/` — captured stock baseline Vector config (`vector-acks-off.toml`) and the acks-enabled
  variant (`vector-acks-on.toml`); they differ only by a `[sinks.<id>.acknowledgements]` block.
- `results/` — raw measurement output.

The acks-on config is applied by setting the CLF to `managementState: Unmanaged`, patching the
`collector-config` configmap, and restarting the collector; restoring `Managed` regenerates the
stock config.

## Implications for the product

1. **`AtLeastOnce` does not currently deliver at-least-once semantics across collector restarts**
   for journald, because end-to-end sink acknowledgements are off by default. This is recorded as a
   known limitation in `.ai/spec/what/log-forwarding.md` (rule 21) and
   `.ai/spec/what/log-collection.md`.
2. **The fix (enable sink `acknowledgements`) is safe to ship from a performance standpoint.**
   Tracked as `[PLANNED: LOG-7538]`.
3. **Open question for the fix:** whether to enable acknowledgements unconditionally for
   `AtLeastOnce`, or only for sources (like journald) whose checkpoint advances on read. The memory
   cost is small and throughput is unaffected either way, so the simplest correct option is to tie
   acknowledgements to `AtLeastOnce`.
